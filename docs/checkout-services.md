# Checkout и Inventory

Реализован backend резервирования. Demo-оплата и защищённое получение оплаченных ключей описаны в [payments.md](payments.md). Frontend checkout не реализован.

## API

Все маршруты находятся под auth:sanctum и EnsureUserIsActive. Чужой заказ возвращает 404.

- POST /api/checkout — 201, включая повтор того же запроса.
- GET /api/orders/{order} — 200, с lazy expiration.
- POST /api/orders/{order}/cancel — 200; повтор безопасен. Оплаченный заказ — 409.

Создание требует заголовок Idempotency-Key: 1–128 ASCII-символов A–Z, a–z, 0–9, точка, дефис, подчёркивание, двоеточие. Заголовок разрешён существующим CORS. Новый checkout требует новый ключ; один и тот же ключ нельзя использовать для изменённой корзины.

```json
{"items":[{"offer_id":12,"quantity":1},{"offer_id":18,"quantity":2}]}
```

Корзина: 1–20 уникальных предложений, положительные целые количества в диапазоне PostgreSQL integer. Повторяющиеся offer_id отклоняются с 422. Поля цены внутри items запрещены. Цена берётся из заблокированной строки offers, валюта EUR. Суммы считаются в целых центах без float, с проверкой диапазона numeric(12,2).

Ответ обёрнут в data и содержит id, status, items (id, offer_id, quantity, unit_price), total_amount строкой, currency и reserved_until в ISO 8601. Ключи, ciphertext, fingerprints, idempotency key и внутренний хеш запроса не возвращаются.

Ошибки: 401 — гость; 403 — blocked; 404 — отсутствующий/чужой заказ; 422 — некорректная корзина, отсутствующий offer, отсутствующий/некорректный ключ идемпотентности; 409 — недостаток товара, неактивное предложение/игра/продавец, изменённая корзина с прежним ключом, конфликт состояния.

## Транзакции и блокировки

Единый порядок: order → offers по возрастанию id → digital_keys по offer_id/id. Для нового заказа INSERT уже удерживает блокировку его строки. Предложения блокируются до чтения цен. Игры и продавцы загружаются пакетно, без отдельного запроса на каждую позицию. Выбор ключей ограничен нужным количеством и использует FOR UPDATE SKIP LOCKED.

CheckoutService создаёт заказ, снимки цен и резервы в одной транзакции. InventoryService централизует изменения ключей. Условный decrement проверяет достаточность счётчика; если не хватает конкретных ключей или счётчика, весь новый заказ откатывается. Методы reserve/release используют собственную транзакцию/savepoint, поэтому перехваченная вызывающим кодом ошибка не оставляет частичную операцию.

Материализованный offers.quantity меняется только available→reserved (-N) и reserved→available (+N). reserved→sold его не меняет. Шифрование и HMAC не затрагиваются.

Checkout/get/cancel повторяют транзакцию до трёх раз при распознанных Laravel deadlock/concurrency errors. Внешних HTTP-вызовов внутри нет.

## Идемпотентность

Новая миграция добавляет nullable orders.idempotency_key и request_fingerprint (для совместимости со старыми заказами), UNIQUE(user_id,idempotency_key). API новых заказов всегда требует ключ.

Корзина нормализуется и сортируется; сервер сохраняет SHA-256 её offer_id/quantity. PostgreSQL pg_advisory_xact_lock(hashtextextended(user_id + key)) сериализует конкурентные запросы ещё до создания строки заказа. UNIQUE остаётся дополнительной гарантией БД.

Тот же ключ и корзина возвращают прежний заказ с прежней ценой и deadline, даже если его статус уже cancelled/expired/paid. Другая корзина — 409. Порядок позиций запроса значения не имеет. Хеш здесь относится к публичному содержимому корзины и не заменяет HMAC цифровых ключей.

Откат миграции отказывается удалять сохранённые idempotency keys, если они уже используются.

## Lazy expiration и освобождение

Резерв — 15 минут; получение заказа не продлевает его. При get/cancel заказ блокируется, просроченный pending_payment освобождается и получает expired. Отмена действующего pending_payment освобождает его и ставит cancelled. История и цены сохраняются.

Перед новым checkout обрабатываются максимум 50 просроченных pending-заказов, содержащих запрошенные предложения. Запрос использует срок резерва, частичный индекс orders и связи/индексы order_items. Это отдельные короткие транзакции ДО захвата предложений нового заказа; чужие заказы не блокируются после offers. Такой порядок исключает очевидный цикл checkout↔expiration.

Каждое освобождение повторно проверяет заблокированный статус, блокирует предложения по id и только reserved-ключи заказа, очищает назначение и deadline, возвращает фактическое количество ключей в счётчик. paid и sold не освобождаются. Конкурентные повторные вызовы не увеличивают остаток повторно.

При большом накоплении просроченных заказов может потребоваться несколько checkout-запросов для очистки backlog из-за лимита 50. Уже выполненное освобождение старых заказов сохраняется, даже если новый checkout затем не удался. Cron/очередей нет; каталог сам по себе резервы не освобождает, счётчик обновляется при lazy expiration.

## Завершение оплаты

InventoryService::confirmSale(Order) вызывается только внутри общей PostgreSQL-транзакции PaymentService (см. payments.md). Сначала заблокировать order, затем вызвать confirmSale, затем отметить подтверждённую попытку succeeded и order paid в той же транзакции. Статус заказа при вызове confirmSale ещё pending_payment.

Метод блокирует offers и ключи в том же порядке, проверяет действительность срока ПОСЛЕ ожидания блокировок, принадлежность и количество всех назначенных ключей. Только reserved переводит в sold, очищает reserved_until, сохраняет order_item_id и не меняет quantity. Просроченный/неполный резерв отклоняется. HTTP-проверка провайдера не должна выполняться под этими блокировками.

Согласование суммы/валюты, достоверность ответа провайдера, идемпотентность payment/webhook и обработка позднего успеха оплаты остаются следующему этапу. Никакой автоматической оплаты или endpoint продажи сейчас нет.

## Проверки

Новая PostgreSQL-suite: tests/Postgres/checkout-services.xml. Используется существующая схема изоляции suites: пустая временная eneba_search_test на отдельной Docker-сети, alias search-postgres, SEARCH_TEST_SANDBOX=1. На рабочей eneba её запускать нельзя. Проверки ограничивают конфигурацию и фактическую базу до миграций.

Конкурентные тесты запускают два независимых PHP-процесса. Третье соединение удерживает gate-блокировку; тест ждёт, пока оба процесса действительно окажутся в PostgreSQL wait_event_type=Lock, и только затем отпускает gate. Проверяются последний ключ, одинаковый idempotency key и одновременные cancel/expiration. checkout-worker.php отказывается работать вне тестового sandbox.

Все тестовые ключи синтетические. Существующий рабочий набор ключей при тестировании не резервируется.
